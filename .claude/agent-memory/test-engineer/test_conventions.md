Test command (from repo root, Git Bash): `node --experimental-vm-modules node_modules/jest/bin/jest.js tests/<file>.test.js`. `jest.config.js` matches `**/tests/**/*.test.js`, `testEnvironment: 'node'`, no transform (plain JS test files, ESM).

Jest globals are NOT auto-injected in this ESM setup. `jest.setTimeout(...)`, `describe`, `test`, `beforeAll`, `afterAll`, `expect` must be imported explicitly from `@jest/globals` if a file needs anything beyond bare `describe`/`test`/`expect` (those three happen to work unimported in practice, but `jest.setTimeout` throws `ReferenceError: jest is not defined` without the import). See [[node-abi-trap]].

Ground-truth discipline established by commit `f775299` (`tests/coverage-oracle.test.js`): grep/scan the SOURCE as ground truth, never the AiDex index itself — a test asserting the index against the index proves nothing. Any new differential/oracle test in this repo should follow that same shape: independent ground truth, then compare against `query()`/`init()` output.

Tests that build a temp project index use `mkdtempSync(join(tmpdir(), ...))` + `rmSync(..., {recursive:true, force:true})` in `beforeAll`/`afterAll`, importing `init`/`query`/`coverage` from `../build/commands/*.js` (compiled output, not `src/*.ts` directly — tests run against the build).

To reconstruct an immutable snapshot of the repo at a pinned commit (avoids ground-truth drift when other agents are editing the live working tree concurrently): `spawnSync('git', ['archive', sha], {cwd: REPO_ROOT})` piped into `spawnSync('tar', ['-x'], {cwd: tmpDir, input: archiveBuffer})`. Both `git` and `tar` are real PATH binaries in this Git Bash environment; `rg` is NOT (see [[node-abi-trap]] sibling note below) — it's a shell function wrapping Claude Code's bundled ripgrep, invisible to `spawnSync('rg', ...)`. Any ground-truth re-scan needed at test time must be pure JS (`fs.readdirSync`/`readFileSync` + `RegExp`), not a shelled-out `rg`.

`query()`'s returned `matches` array is sorted by `file` then `lineNumber` (src/commands/query.ts, `allMatches.sort`), NOT by relevance/item-rank. To measure the rank of a specific item under `contains`/`starts_with` mode, exploit that `searchItems`' SQL `ORDER BY` (src/db/queries.ts) is a strict total order, making window membership monotone in `itemLimit`: binary-search `itemLimit` in `[1, itemsTotal]` for the minimal value at which the target `{file, lineNumber}` occurrence appears.

`build/` is gitignored (`.gitignore:5`), so proving a new test bites can edit the COMPILED `.js` output directly instead of touching `src/*.ts` (which would violate the test-only mandate and require a rebuild+retest+revert dance anyway). Pattern used successfully for spec_90f49672 (whitespace-tolerance tests): `cp build/X.js /tmp/X.js.bak`, one-line `Edit` to neutralize the behavior under test (e.g. `const normTerm = term; // BROKEN FOR TEST` instead of calling the normalizer), rerun the targeted jest file to see the expected subset go red, then `cp /tmp/X.js.bak build/X.js` back (or just `npm run build` from clean `src/` — safer, guarantees no leftover mutation). When two call sites share one normalization function, break each independently (one commented-out call at a time) to prove BOTH are load-bearing and that the failing test subsets are disjoint/complementary — a single combined break can't tell you which site a given test actually depends on.


**Native-addon-per-process trap (card 39e02f07, spec_ef8b08fb, 2026-08-12):** tree-sitter's native addon is a process-level singleton, but jest gives every test FILE its own vm context. Under `--runInBand` / `--maxWorkers=1` all files share one process, so past the first live-indexing file `parseFile()` returns `rootNode: undefined` and `extract()` throws on `node.startPosition` -- reads exactly like a parser bug, is not one. Symptom-based guards (asserting `rootNode` is defined) are WORTHLESS here: they only fail for whichever file jest happens to run second, and jest's file order comes from a cached-timings heuristic that varies run to run (measured: 64/36/52 failures across 3 identical `--maxWorkers=1` runs). The correct guard checks the EXECUTION MODE, not the symptom: a `globalSetup` hook (`tests/guards/no-single-worker.globalSetup.js`, wired via `jest.config.js`'s `globalSetup` field) reading `globalConfig.maxWorkers === 1` and throwing before any worker/test exists -- order-independent by construction, fires in under 400ms. Note `globalConfig` has NO `runInBand` field; `--runInBand`/`-i` normalizes to `maxWorkers = 1` internally (confirmed empirically: both flags produce byte-identical `maxWorkers=1` in the guard's error message), so checking `maxWorkers` alone covers both spellings -- don't waste a destructure on `globalConfig.runInBand`, it reads `undefined` always.

**cwd-anchored test roots break when launched from outside the repo:** any `const REPO_ROOT = process.cwd()` (or similar) in a test file breaks (ENOENT / Cannot find module) the moment the suite is invoked from a directory other than the repo root -- e.g. `agent-forge verify` steps, or a CI runner with a different working directory. Fix is mechanical and behavior-preserving from the repo root: `const REPO_ROOT = dirname(dirname(fileURLToPath(import.meta.url)));` (two `dirname` calls because the test file itself lives in `tests/`, one level below the root). Verified clean by running the full suite with `--rootDir` pointed at the repo while `cwd` was `/tmp`.
